## A. 密钥与认证

**Q1. OPAQUE `export_key` 作为 KEK 派生输入**
`KEK = HKDF(salt, export_key, "kek-v1")`，salt 为 16 字节随机且公开存储。`export_key` 在 `@serenity-kit/opaque` 中的语义是否符合此用途？是否有更推荐的派生路径或需要额外域分离？

**Q2. 两份 UK 包裹副本**
用户同时持有 `kek_wrapped_uk`（本人登录解包）与 `wrapped_uk`（管理员用 TK 解包，用于口令重置）。这两份副本并存是否引入额外的攻击面？是否应改为单一副本 + 管理员代办重置？

**Q3. 离线 Argon2id 缓存 UK**
可选功能：用 Argon2id(m=65536,t=3,p=4) 派生本地 KEK 解包缓存的 UK，支持离线解锁。请评估安全与体验的权衡——是否值得保留，还是应强制在线认证？

**Q4. Shamir 分片展示流程**
3 份分片通过浏览器界面逐份展示、要求管理员分别保存到离线介质。请评估截屏、肩窥、浏览器扩展、剪贴板等泄露路径，并给出具体的流程改进建议。

**Q5. 分片校验锚点**
服务端只存 `tk_hash = SHA-256(TK)` 用于重构校验。在 TK 为 256-bit 随机的前提下，裸 SHA-256 是否足够？有无理由改成 HMAC 或带域分离的 KDF？

## B. 租户隔离与密钥轮换

**Q6. 三层隔离的充分性**
应用层强制 `tenantId` + 复合外键 + PostgreSQL RLS 的三层设计，是否存在可绕过的路径？特别关注：`tenants` 表为认证需要未启用 RLS，应用账号权限边界应如何界定？

**Q7. 设备签名防重放（重要）**
当前敏感操作的签名 Payload 形如 `update-item:<id>:<version>`、`audit:<prevHash>:<hash(sealedEvent)>`，不含时间戳、随机数或请求唯一 ID。请评估重放风险，并给出最小改动的防重放方案（例如服务端下发一次性挑战、Payload 纳入 `exp` 与 `nonce`）。

**Q8. VK 轮换的原子性**
成员离职时轮换 VK 并重包裹所有 DEK（见协议 §5.6）。评审清单第 4 项要求确认该过程的原子性与失败恢复。当前设计是后台分批任务，中途失败会出现"部分 DEK 用旧 VK、部分用新 VK"。请评估是否可接受，以及客户端应如何安全处理混合状态。

**Q9. DEK 的 nonce 计数由客户端上报**
`items.nonce_count` 由客户端加密时递增并上报。若客户端 bug 或恶意代码将其重置，可能突破 AES-GCM 的 nonce 预算。是否应由服务端按写入次数独立计数作为第二道防线？

## C. 审计链

**Q10. 哈希公式与长度编码**
`H = SHA256(prev || UTF8(String(aadLen)) || aad || ct || tag || UTF8(ts))`，其中 aadLen 是十进制字符串。请确认该编码是否有歧义（例如不同 aadLen 与 aad 组合产生相同字节序列），是否应改为固定宽度整数。测试向量见 `test-vectors.md` §3。

**Q11. 并发顺序一致性**
PostgreSQL 实现使用 `SELECT ... FOR UPDATE` 锁租户链头 + 事务内插入并推进。请确认该方案在高并发下无分叉、无死锁，并评估是否需要按 Vault 拆分多条链以提升吞吐。

**Q12. 整段回滚**
哈希链只能防"改一条"，不能防"删掉整段后重算 + 时间戳伪造"。当前计划用每日根哈希外部锚定（邮件/第三方透明日志）。请评估该锚定方案在平台被完全控制时是否仍有效，以及最小可信通道要求。

**Q13. 审计员的验证起点**
审计员客户端从创世哈希逐条重算。若平台向不同审计员提供不同长度的链（分叉视图），仅靠链本身能否检测？外部锚定需要如何配合才能检出"视图分叉"？

## D. Web 零知识的固有风险

**Q14. 代码下发攻击面**
服务端下发的前端代码若被替换为恶意版本，可在用户会话中读取明文。当前缓解：CSP、SRI、构建签名、加密模块开源可审；高保密客户走自托管。请评估这些缓解的实际有效性，以及是否应增加"关键加密操作在独立 iframe/扩展中隔离"等更强措施。

**Q15. 明文驻留与内存擦除**
明文在浏览器内存中解密后渲染。JS 无法可靠擦除字符串内存。请评估该风险的实际可利用性，以及是否有浏览器侧的最佳实践（如 ArrayBuffer + `zeroize`、避免字符串化）值得纳入实现规范。
