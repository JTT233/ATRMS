# 协议测试向量 v0.1

> 这些值由 `node:crypto` 与 `packages/crypto` 实际计算得出，用于评审者独立复现。
> 所有输入均为构造值，不含任何真实密钥或租户数据。

## 1. 创世哈希

新租户初始化审计链头时使用：

```
genesis_hash = SHA256( UTF8("genesis:v1:" || tenant_id) )
```

| 项 | 值 |
|---|---|
| `tenant_id` | `11111111-1111-4111-8111-111111111111` |
| 输入字符串 | `genesis:v1:11111111-1111-4111-8111-111111111111` |
| **期望输出（hex）** | `1b6fcaff03181e700f720e06e973685346135c3fb3c85d43bd47ec54bf2301c1` |

## 2. AAD 的确定性序列化

`EnvelopeContext` 按**固定字段顺序**序列化，无空白：

```
ctx = { tenantId, vaultId, type, objectId, version }
aad = JSON.stringify(ctx)   // 键顺序如上，不使用通用 canonical JSON
```

| 项 | 值 |
|---|---|
| `tenantId` | `t-1111` |
| `vaultId` | `v-2222` |
| `type` | `item` |
| `objectId` | `i-3333` |
| `version` | `1` |
| **期望 aad** | `{"tenantId":"t-1111","vaultId":"v-2222","type":"item","objectId":"i-3333","version":1}` |

**注意（需评审确认）：** 实现依赖"字段顺序固定"而非 RFC 8785 canonical JSON。因为 `EnvelopeContext` 是封闭结构、由代码构造而非外部输入，所以顺序恒定；但若未来增加可选字段或允许外部传入 `ctx`，必须改用真正的确定性序列化，否则同一上下文可能产生不同 AAD，导致合法密文无法解密。**请评审此判断是否可接受。**

## 3. 审计链哈希

```
H_i = SHA256( prev_hash_bytes
              || UTF8(String(aad_bytes.length))
              || aad_bytes
              || ct_bytes
              || tag_bytes
              || UTF8(timestamp) )
```

注意长度前缀是 **aad 的 UTF-8 字节数的十进制字符串**（不是固定 4 字节大端整数），这是当前实现的既有约定，评审需确认是否改为更常见的固定长度编码。

| 项 | 值 |
|---|---|
| `prev_hash` | `07` 重复 32 次（64 个 hex 字符） |
| `aad` | `{"tenantId":"t-1111","vaultId":"v-2222","type":"audit","objectId":"a-4444","version":1}` |
| `aad` 字节数 | 84 |
| `ct` | `0102030405060708`（8 字节） |
| `tag` | `a1` 重复 16 次（16 字节） |
| `iv` | `00` 重复 12 次（信封内，不参与哈希） |
| `timestamp` | `2026-11-24T00:00:00.000Z` |
| **期望 hash（hex）** | `299b7dce529cee9ab1c77582226848cdb869cd71e6c61afefb7dc664aa70c7db` |

传输用的 `sealedEvent` 是信封 JSON 的 UTF-8 hex：

```
信封 JSON = {"v":1,"alg":"AES-256-GCM","iv":"000000000000000000000000","ct":"0102030405060708","tag":"a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1a1","aad":"{...}"}
```

## 4. 复现方式

在仓库根目录执行（需已安装依赖）：

```bash
npm test
```

其中 `apps/api/src/app.test.ts` 的用例「服务端哈希与加密核心包逐字节一致」会同时调用：

- `packages/crypto` 的 `auditHash()`（浏览器端实现）
- `apps/api` 的 `computeAuditHash()`（服务端实现）

并对同一输入断言两者输出相同。若评审者希望独立复现，可用上表的原始参数按公式手算，与 `HASH` 值比对。

## 5. 已知需要评审确认的编码选择

1. AAD 用固定字段顺序而非 RFC 8785（见 §2）；
2. 审计链长度前缀用十进制字符串而非固定宽度整数（见 §3）；
3. `tk_hash` 用裸 SHA-256 而非 HMAC/KDF（TK 本身是 256-bit 随机值，无字典攻击面）；
4. 设备签名 Payload 目前不含时间戳或随机数，需评估重放窗口（见 `review-questions.md` Q7）。
