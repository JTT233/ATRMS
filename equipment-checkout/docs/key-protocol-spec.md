# 器材借还管理系统｜密钥协议规格 v0.1

> Phase 0 交付物，目标读者：外部密码学评审者。
> 本文描述原语、参数、密钥层级、协议流程与不变量。实现须严格遵循版本号，禁止降级。

---

## 1. 符号与编码

| 记号 | 含义 |
|---|---|
| `TK` | 租户主密钥，32 字节随机 |
| `UK_u` | 用户 u 的密钥，32 字节随机 |
| `VK_v` | 保险库 v 的密钥，32 字节随机 |
| `DEK_i` | 器材 i 的密钥，32 字节随机 |
| `AK` | 审计密钥，32 字节随机 |
| `Enc(k, m, aad)` | AES-256-GCM 加密，随机 96-bit IV，输出 `iv‖ct‖tag` |
| `Wrap(k, key, aad)` | 用 `Enc` 包裹 32 字节密钥，aad 注明用途 |
| `HKDF(salt, ikm, info)` | HKDF-SHA-256，输出 32 字节 |
| `H(x)` | SHA-256 |
| `‖` | 字节拼接 |

所有随机数来自 `crypto.getRandomValues`。密钥不得以字符串形式出现在日志、错误上报、URL 或持久化明文中。

---

## 2. 原语与参数

| 用途 | 原语/参数 |
|---|---|
| 口令认证 | OPAQUE（ristretto255-SHA512 ciphersuite），服务端只存 credential record；使用 `export_key` 派生 KEK |
| 离线解锁（可选） | Argon2id，m=65536 KiB，t=3，p=4，hashLen=32，salt=16 字节随机 |
| 密钥派生 | HKDF-SHA-256，info 必须带版本与用途标签，如 `kek-v1`、`uk-wrap-v1` |
| 内容加密 | AES-256-GCM，随机 96-bit IV，16 字节 tag；AAD 绑定上下文（见 §3） |
| 设备签名 | Ed25519，私钥在浏览器生成并设为 non-extractable；公钥登记到服务端 |
| 审计链 | `H_i = H(H_{i-1} ‖ len(aad) ‖ aad ‖ ct_i ‖ ts_i)` |
| 恢复分片 | Shamir 2-of-3，阈值 2；分片 Base32 编码带校验和，仅在恢复设备内存中重构；重构后必须用预先保存的 `H(TK)` 校验，不一致即拒绝（分片库不自带结果验证） |

**GCM nonce 预算：** 同一把 DEK 加密次数上限 2^32；接近上限必须轮换 DEK。实现层维护计数并在达到阈值前强制轮换。

---

## 3. 密文信封与 AAD 绑定

每条密文使用带版本的信封：

```
Envelope = {
  v: 1,
  alg: "AES-256-GCM",
  iv: 12 bytes,
  ct: bytes,
  tag: 16 bytes,
  ctx: { tenant_id, vault_id, type, object_id, version }
}
```

`aad = canonical_json(ctx)`。上下文含 `type`（item/loan/audit/...）与 `version`，用于阻止密文跨对象、跨租户、跨版本重放或调包。解密前必须校验 `ctx` 与本地期望值一致，不一致立即拒绝。

密钥包裹使用 `Wrap(k, key, aad="wrap-v1:"‖purpose‖":"‖object_id)`。

## 4. 密钥层级

```
恢复分片(2-of-3) ──重构──> TK
                            ├─ Wrap ─> UK_u   （每位成员）
                            ├─ Wrap ─> VK_v   （每个保险库）
                            │            └─ Wrap ─> DEK_i ──Enc──> 器材字段/照片/缩略图
                            └─ Wrap ─> AK     （每租户一把）
```

用户口令不直接包裹 UK：登录经 OPAQUE 得到 `export_key`，`KEK = HKDF(salt, export_key, "kek-v1")`，再用 KEK 包裹/解包 UK。离线解锁使用 Argon2id 派生本地 KEK 解包本地缓存的 UK；该缓存可由组织策略禁用。

## 5. 协议流程

### 5.1 租户创建

1. 组织管理员在浏览器生成 `TK = random(32)`。
2. 用 Shamir 2-of-3 分割 TK，得到 3 份分片；通过界面逐份展示，要求管理员分别保存到离线介质，并逐份确认。
3. 生成 `AK = random(32)`，用 TK 包裹后上传。
4. 创建首个 Vault：`VK = random(32)`，用 TK 包裹后上传。
5. 服务端只保存包裹后的 blob、tenant_id 与阈值配置；**分片不上传**。

### 5.2 成员邀请与注册

1. 管理员生成邀请令牌（一次性、限时）。
2. 被邀请人完成 OPAQUE 注册；客户端生成 `UK = random(32)`，用 `KEK` 包裹上传。
3. 管理员客户端用 TK 解出 `VK`，为被邀请人生成 `UK` 的 TK 包裹副本（用于组织恢复），写入成员记录。
4. 按角色赋予 Vault 权限：用管理员解出的 `VK` 包裹后写入 `memberships`。

> 步骤 3 要求管理员在线；若管理员不在线，邀请进入待批准状态，不降级为平台代管密钥。

### 5.3 登录与新设备绑定

1. OPAQUE 登录 → `export_key` → `KEK` → 解包 `UK`。
2. 拉取该用户被授权的 `VK` 包裹副本，用 `UK` 解出 `VK`。
3. 生成设备 Ed25519 密钥对，私钥设为 non-extractable；公钥提交管理员批准或经 2-of-3 恢复流程批准。
4. 已登记设备对敏感操作（成员变更、密钥轮换、恢复、导出）签名；服务端验证签名后才受理。

### 5.4 器材创建 / 更新

1. 生成 `DEK = random(32)`，随机 128-bit QR token。
2. 用 DEK 加密字段、原图、缩略图，AAD 分别绑定 `vault_id / item_id / version / type`。
3. 用 `VK` 包裹 DEK；上传密文信封与 wrapped DEK。
4. 写审计事件（见 §5.8）。更新器材时递增 version，必要时轮换 DEK。

### 5.5 借出 / 归还

1. 扫码得到 QR token → 服务端返回密文信封（不含任何明文）。
2. 客户端解出 DEK、解密器材与借还记录，按 RBAC 判断是否允许操作。
3. 生成借出/归还记录密文（含借用人和状态照片），AAD 绑定 loan id 与 version。
4. 设备私钥签名操作摘要 → 上传记录、更新器材状态与版本 → 写审计事件。
5. 服务端只更新 status/version 字段，不解析业务内容。

### 5.6 成员移除与密钥轮换

1. 管理员撤销成员资格、吊销其设备公钥。
2. **轮换 VK**：生成新 `VK'`，用 TK 重新包裹；为每位剩余成员用其 UK 重新包裹 `VK'`。
3. **重包裹 DEK**：用 `VK'` 重新包裹所有相关器材的 DEK（后台任务，可分批）。
4. 写审计事件，记录轮换范围与时间。
5. 注意：被移除设备已缓存的明文无法远程擦除，此为契约中明示的残余风险。

### 5.7 口令重置 / 组织恢复

**个人口令重置（仍有 UK 包裹副本可解）：** 管理员用 TK 解出该用户 UK，生成新的 KEK 包裹副本；用户用新口令完成 OPAQUE 注册流程并解出同一 UK。UK 不变，因此历史数据仍可读。

**组织恢复（管理员全部丢失口令）：**
1. 两名管理员在各自设备输入恢复分片；分片只在本地浏览器内存中存在。
2. 恢复设备通过 Shamir 重构 TK；重构完成后立即擦除分片内存。
3. 用 TK 解出 AK、VK 与必要的 UK 包裹副本，为管理员建立新的认证凭据。
4. 全过程写审计事件；平台无法参与，也无法看到 TK。

**1-of-3 分片必须失败**，这是测试判据。

### 5.8 审计日志写入与验证

1. 事件内容用 AK 加密；`H_i = H(H_{i-1} ‖ len(aad) ‖ aad ‖ ct_i ‖ ts_i)`。
2. 服务端保存 `ct_i, H_i, H_{i-1}, ts_i`，无法生成有效链（无 AK 且不知历史哈希原文结构）。
3. 审计员客户端从创世哈希逐条重算并比对；任一条不匹配即报警。
4. 每日根哈希通过独立通道（邮件/第三方透明日志）锚定给组织，防止整段回滚。

## 6. 不变量与安全性质

1. 平台在任何时刻都不持有 TK/UK/VK/DEK/AK 的明文或可重构材料。
2. 口令与恢复分片从不明文离开客户端，也不进入日志/崩溃上报。
3. 密文 AAD 绑定租户、保险库、对象类型、对象 ID、版本，阻止重放与调包。
4. 同一密钥下 GCM IV 不重复；达到预算前轮换密钥。
5. 成员移除后，其账号与设备无法解出新轮换的 VK 及后续内容。
6. 审计链任何单点修改/删除/插入/重放均可被客户端检出。
7. 所有协议版本号显式携带；禁止静默降级。

---

## 7. 已知限制（需评审确认）

- **Web 代码下发**：恶意前端可在用户会话中读取明文；缓解见威胁模型 T02，根治依赖自托管。
- **端点被控**：无法防御。
- **元数据**：时间戳、密文大小、扫码事件仍可见。
- **OPAQUE / Argon2id wasm 实现**：需在评审前锁定具体库版本并完成依赖审计。
- **Shamir 实现**：需选用审计过的库；自研实现必须给出测试向量。
- **AAD 规范化**：`canonical_json` 必须使用确定性序列化（键排序、无空白），实现需附测试向量。

---

## 8. 评审清单

请外部评审者重点确认：
1. OPAQUE `export_key` 用作 KEK 是否符合所选库的安全建议；
2. 离线 Argon2id 缓存 UK 是否值得保留（安全 vs 离线体验权衡）；
3. Shamir 2-of-3 的分片存储与展示流程是否存在社会工程/截屏泄露问题；
4. VK 轮换时重包裹 DEK 的原子性与失败恢复；
5. 审计链在并发写入下的顺序一致性。
