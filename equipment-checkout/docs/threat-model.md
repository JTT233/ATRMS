# 器材借还管理系统｜威胁模型 v0.1

> Phase 0 交付物。适用部署：多租户 SaaS（默认）+ 单租户自托管（预留）。
> 目标：在写代码前把"谁可能怎么攻击、我们靠什么挡、还剩什么风险"说清楚。

---

## 1. 范围与共同假设

- 系统只负责**器材位置与借还责任的记录、审计与提醒**，不保管实物，不处理支付卡号。
- 平台运营方拥有基础设施与代码分发权，但**不持有任何客户数据解密密钥**。
- 客户端运行环境（浏览器）默认是用户可控但可能被恶意软件感染的终端；我们不假设终端可信。
- 自托管形态下，客户自己掌握基础设施与部署产物，平台不接触其数据与密钥。

---

## 2. 资产清单

| 资产 | 敏感性 | 说明 |
|---|---|---|
| 租户主密钥 TK | 极高 | 每租户唯一，由 2-of-3 分片重构；泄露等于该租户全部数据失守 |
| 用户密钥 UK / 保险库密钥 VK / 审计密钥 AK | 极高 | 由 TK 包裹，任何一把泄露都会缩小攻击面到对应范围 |
| 器材密钥 DEK | 高 | 每件器材一把，泄露只影响单件器材 |
| 器材字段、照片、借还记录、维保信息 | 高 | 业务明文，仅在客户端存在 |
| 审计链完整性 | 高 | 一旦可篡改，责任举证体系失效 |
| 二维码 token | 中 | 128-bit 随机，泄露本身不泄露内容，但可伪造扫码事件 |
| 元数据 | 中 | tenant_id、vault_id、item_id、时间戳、密文大小、邮箱、登录/扫码事件 |
| 系统可用性 | 中 | 被 DoS 时借还业务停摆，但数据不丢（可导出） |

## 3. 参与者与信任边界

| 参与者 | 能力 | 信任级别 |
|---|---|---|
| 外部攻击者 | 网络、API、公开网页 | 不信任 |
| 其他租户用户 | 正常账号、可调用 API | 不信任 |
| 组织内借用人/保管员/审计员 | 合法账号、可扫码 | 受限信任（RBAC） |
| 组织管理员 | 管理成员与密钥、持有恢复分片 | 高信任，但分片需分离保管 |
| 平台运维 | 基础设施、代码发布、数据库访问 | **不信任其访问明文**（零知识设计前提） |
| 供应链（npm/wasm/云） | 依赖包、构建产物 | 不信任，需锁定与审计 |
| 离职员工 | 曾拥有合法账号与已下载明文 | 不可信，需主动撤销 |

**边界原则：** 明文与所有主密钥跨不过客户端边界；服务端边界内只有密文、随机 ID、时间戳与必要认证信息。

## 4. 攻击者画像

| 攻击者 | 目标 | 主要手段 | 关键缓解 |
|---|---|---|---|
| 外部攻击者 | 窃取数据 / 勒索 | 拖库、API 越权、XSS、依赖投毒 | 服务端无明文；AAD 绑定；CSP；SCA |
| 恶意或被攻陷的平台 | 读取客户数据 | 下发恶意 JS、直接读库 | 零知识架构；构建签名；开源审计；自托管选项 |
| 其他租户 | 横向渗透 | 猜 ID、重放 token、越权请求 | 独立 TK；AAD 含 tenant_id；强制隔离测试 |
| 组织内越权用户 | 看不该看的器材 | 改角色、抓包 | RBAC 客户端判定；审计记录；Vault 隔离 |
| 离职员工 | 继续访问 / 泄露 | 复用旧设备缓存 | 轮换 VK/DEK、吊销设备、制度与 MDM |
| 社会工程攻击者 | 拿到恢复分片 | 冒充管理员索取分片 | 2-of-3 阈值、分片持有者分离、恢复审计 |
| 法律/监管压力 | 要求提供明文 | 传票、配合调查 | 架构上无法提供；法务前置说明 |

## 5. 威胁矩阵

| 编号 | 威胁 | 影响 | 缓解措施 | 残余风险 | 验证方式 |
|---|---|---|---|---|---|
| T01 | 服务端数据库/对象存储泄露 | 高 | 全量密文；平台无密钥 | 低（元数据仍泄露） | 拖库模拟：拿到的全是密文 |
| T02 | 平台下发恶意前端代码窃取密钥 | 极高 | CSP、SRI、构建签名、加密核心开源可审、自托管 | **中高**（Web 固有） | 代码签名校验演练 |
| T03 | 跨租户越权读取/重放 | 高 | 每租户独立 TK；AAD 绑定 tenant_id；API 强制 tenant 隔离 | 低 | A 租户密钥解 B 租户数据必须失败 |
| T04 | 组织内角色越权 | 中高 | RBAC + Vault 范围在客户端判定；服务端只管密文归属 | 中（端点被控时失效） | 角色矩阵测试 |
| T05 | 离职员工设备残留明文 | 高 | 轮换 VK/DEK、吊销设备、审计、SLA 告知 | **高**（技术不可擦除） | 离职交接演练 + 条款确认 |
| T06 | 恢复分片被套取/合谋 | 极高 | 2-of-3 阈值，分片管理员分离；恢复写审计 | 中（内部合谋） | 1-of-3 必须失败 |
| T07 | 审计日志被删除/回滚/重放 | 高 | 哈希链 + 每日根哈希外部锚定 | 中（锚定通道被控） | 篡改任一事件必须报警 |
| T08 | 二维码被枚举或调包 | 中 | 128-bit 随机 token；限流；归还拍照留证 | 中（实体标签被替换） | token 熵与限流测试 |
| T09 | 元数据推断业务 | 中 | 不存 IP；随机 ID；可选大小填充；日志 30 天 | 中（时间/频率仍可见） | 日志审查 |
| T10 | XSS / npm wasm 依赖投毒 | 高 | 严格 CSP；lockfile；SCA；加密核心独立审计 | 中 | 依赖审计 + 渗透测试 |
| T11 | 传输中间人 | 高 | TLS 1.3 + HSTS；证书固定（可选） | 低 | TLS 扫描 |
| T12 | 服务不可用 / 勒索 | 中 | 加密导出、对象存储版本控制、自托管、备份 SLA | 中 | 灾备演练 |
| T13 | 法律要求交出明文 | 高 | 零知识架构只能交密文；隐私政策与合同前置说明 | 中（合规不确定性） | 法务评审 |

## 6. 部署形态差异

| 维度 | SaaS | 自托管 |
|---|---|---|
| 平台可见范围 | 密文 + 元数据 | 无（平台不部署） |
| 代码下发风险 | 存在，靠签名与审计缓解 | 由客户控制发布流程，基本消除 |
| 密钥归属 | 客户组织（分片离线） | 客户组织 |
| 升级与运维 | 平台负责 | 客户负责 |
| 合规 | 平台需等保/个保法 | 客户自行合规 |
| 适用客户 | 中小组织 | 高保密/强合规组织 |

---

## 7. 明确接受的风险

1. **端点被攻陷**：用户设备中毒后，攻击者可直接读取内存中的明文，任何加密架构都无法阻止。
2. **离职设备明文残留**：只能阻止后续同步，不能远程擦除已下载内容。
3. **元数据可见**：服务端知道谁在何时同步了多大密文、扫了哪个 token；可通过填充与日志最小化降低，但无法归零。
4. **浏览器代码下发**：这是 Web 零知识的结构性弱点；自托管是彻底解法。
